# Maintenance cleanup and locking

- Every Yandex move/removal requires a prior PostgreSQL `document_cleanup_queue` row and the guarded executor.
- Owner-approved `filename_newlines` resource moves may address a basename containing CR/LF solely to replace those line breaks with spaces in the same directory. The persisted target must match that exact normalization. After remote identity verification, the database phase checkpoints only the matching catalog source path with revision checks and audit history. Other control characters, unapproved plans, overwrite, and directory changes remain rejected; ordinary Sync never creates these repair plans automatically.
- `maintenance.monocorpus_sync` applies persisted cleanup and synchronizes the catalog. Duplicate-MD5 resources may be queued during traversal; unrestricted missing links may be published, but restricted links may not.
- Cleanup is an exception to deferred catalog writes: execute persisted plans before traversal, and persist/execute discovered zero-byte or duplicate-resource plans at file boundaries during traversal. Safe stop finishes the current cleanup operation. Completed cleanup is retained even when the buffered catalog commands are discarded; unexecuted or failed plans remain durable for the next run. Pending document cleanup excludes its MD5; resource cleanup excludes only its source path.
- A document-scoped move completes only after target identity verification, managed S3 derivative removal, and dependent PostgreSQL cleanup. Resource-scoped moves/deletions affect only the named Yandex resource. Execution resumes from the persisted phase, revalidates source MD5/resource ID, and never overwrites an existing target.
- Document cleanup also removes completed entries for the MD5 from the shared local source cache. Pending ISBN reviews are reconciled in the same PostgreSQL transaction as document deletion: missing candidates are removed, obsolete groups are superseded, and decided reviews remain unchanged as audit history.
- Use the catalog-owned document deletion path and verify file-owned foreign-key cascades and retained checkpoints. Deleting a catalog document retains its publication, including when the publication becomes empty, and preserves shared bibliographic data and audit history. Explicitly remove detached `library_upstream_metadata` for the MD5 in the same transaction. `document_cleanup_queue` is audit/control state and survives document deletion.
- Catalog sync and Backblaze upload may run concurrently. Upload checkpoints must revalidate the pending row's source identity and remove objects created by stale attempts.
- New move targets preserve the complete path relative to the configured document source root under `filtered_out/<reason>/`. Persisted targets are immutable and remain resumable even when target policy changes later.
- Library cleanup preparation marks existing Pascal catalog rows as `non_document`. Newly discovered Pascal files are filtered by catalog sync like other non-document files.
