# Maintenance document storage

- Backblaze B2 via S3 is primary document and derived storage under `documents.primary_storage`.
- `maintenance.monocorpus_sync` owns Yandex Disk traversal, catalog discovery, unrestricted publishing, and guarded cleanup. It never downloads document bytes or uploads document content.
- New MD5 discovery creates publication, document, and Yandex source location atomically. Sync preserves selected files and bibliographic facts, respects protected file fields before publication, and never widens persisted privacy. Unchanged facts do not create audit revisions.
- Restricted catalog documents must persist null `ya_public_url` and `ya_public_key`, including when Yandex metadata or an existing row contains public links. Catalog sync does not revoke Yandex publication.
- Catalog traversal matches MD5s against one normalized PostgreSQL snapshot and buffers ordinary catalog commands in memory until traversal finishes. Virtual source choices deduplicate new MD5s without changing persisted publication membership. Canceling or aborting traversal discards the buffer; the next run traverses again. Cleanup remains an exception under [cleanup guidance](cleanup.md).
- Invalid resource paths are skipped with an escaped path diagnostic and a counted failure; valid resources continue to the apply phase. Invalid configured roots and resources outside the configured root remain fatal. Skipping an invalid directory skips its subtree; the run remains failed until the source path is corrected.
- After traversal, apply at most 250 unique MD5 commands per PostgreSQL transaction with set-based writes and audit insertion. Lock and revalidate current document/source revisions, protected fields, verified MIME, privacy, and active cleanup ownership before mutation. Conflicted files remain unchanged and surface actionable failures; other valid files in the batch can commit. New publication/document/source records commit together. Stop between committed batches; never hold a database transaction during traversal or storage requests.
- Publish missing unrestricted links only after catalog acceptance. Recheck catalog privacy/revisions and remote identity immediately before each request, then checkpoint returned links in bulk. Safe stop finishes the current request and flushes completed link checkpoints; the next traversal recovers links already published in Yandex. Progress and summaries distinguish scanned resources, buffered/committed/pending catalog commands, and pending publications.
- Missing, invalid, or replaced canonical paths are restored from a discovered file with the expected MD5; never check an empty canonical path in Yandex. Duplicate cleanup requires a surviving canonical resource with the same MD5, including a canonical source buffered for later catalog insertion.
- `maintenance.sync_documents_s3` runs only through the independent automatic/manual Backblaze GitHub workflow, never the CLI or Yandex discovery. Its internal runner uses the shared task runtime with stdout-only logs, progress, persisted per-item `task.artifact` outcomes, and a final structured summary. See `docs/operations.md` for workflow configuration and limits.
- Transfer pages normalized existing catalog documents in deterministic MD5 batches of 250. Pending means a missing/blank primary locator or missing size, nonblank ETag, or verification timestamp. Complete checkpoints are left alone; incomplete existing checkpoints are verified/repaired while preserving valid destinations. Never insert a document/publication, filter by inclusion/selected-file status, or automatically redirect invalid/privacy-inconsistent locators.
- Exclude active document cleanup and plans owning the canonical source path. Unknown privacy fails closed; known restricted files use the private bucket and encrypted locators. Preserve protected facts, and refuse changes to protected checkpoint fields. Snapshot source/document/primary identity and revisions; checkpoint in a short guarded transaction with revision/audit writes.
- HEAD the destination before acquiring bytes. Matching expected source size plus submitted `source-md5` metadata or a plain MD5 ETag permits reuse without download; a multipart ETag alone does not. If source size/evidence is insufficient, acquire a verified source before trusting the object. Confirm uploads with HEAD, never a B2 verification download.
- When bytes are needed, reuse an MD5-valid shared cache entry without deleting it, otherwise download directly from the persisted Yandex path into a private transfer-owned temporary directory. Revalidate remote source identity and MD5/size, check disk capacity with a 1 GiB reserve, and remove owned completed/partial files on success or failure. Transfer does not populate or globally prune the shared cache.
- Abort incomplete multipart uploads only for the exact target key; preserve flat `{md5}{extension}` keys and existing valid managed locators. Restricted-object cleanup requires current catalog identity/privacy and verified public-object identity before deletion; confirm removal before committing.
- Use shared per-document operation locks and safe boundaries described in [cleanup guidance](cleanup.md). Item failures/unavailable sources/deferred documents remain unresolved, other documents continue, and targeted incomplete work returns nonzero. Empty backlog succeeds. Safe stop finishes the current document; deterministic B2 objects recover uploads whose database commit failed.
- During catalog traversal, persist and execute a resource-scoped `corrupted` move for every zero-byte file before publication or catalog insertion. Resource scope keeps distinct empty paths independent despite their shared MD5.
- Pascal source files (`.pas` or `text/pascal`) follow the ordinary non-document sync filter on every run. Existing catalog rows remain available to Library cleanup preparation; sync does not create cleanup plans for uncataloged Pascal files.
