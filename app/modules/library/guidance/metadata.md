# Library metadata processing

## Discovery and ownership

`library.metadata_extract` extracts missing metadata first and then reassesses existing metadata against source evidence. PostgreSQL `catalog_publications.metadata_review_order` owns the queue: `0` is unextracted, positive positions are ordered oldest first, and `-1` permanently protects admin-validated publication metadata. A successful extraction, unchanged/changed review, or committed proposal atomically receives the next sequence position; failures and local deferrals retain their position. The sequence is queue order, not review count, so new publications join the back after initial extraction without catch-up reviews. Equal positions prioritize missing title, then missing author, then publication ID. The run captures a sequence ceiling and advances a composite cursor, preventing its own saves from re-entering the queue. At each loop iteration, one PostgreSQL SELECT chooses up to 200 unmerged publications with eligible evidence and no pending task metadata review, then aggregates normalized metadata and ordered source details for that batch. Independent child aggregates avoid multiplying rows across unrelated relations. Python renders Schema.org from the returned envelope and checks local retry state; it never invokes the single-document reader during discovery.

Release the connection before processing each batch sequentially. Continue from its last queue position/title-gap/author-gap/publication-ID tuple even when local deferrals exclude every item, so a run never cycles on failed/deferred publications. Stop when the candidate query returns no rows, the eligible-publication limit is reached, safe stop is requested, or a fatal/global provider outcome prevents work. Each query observes a fresh statement snapshot; mutations recheck source/publication revisions and metadata. No full-run candidate inventory or quality cache is built. Progress totals count eligible publications fetched so far; `scanned` counts queried publications, and `inventory_exhausted` identifies an empty-query termination rather than a limit/stop/abort.

`maintenance.monocorpus_meta_evaluate` chooses up to 200 MD5-ordered unrestricted files of unmerged publications with existing metadata, a configured Tatar language, pending file inclusion or included files without classification, verified usable evidence, and no pending task metadata review. One PostgreSQL SELECT aggregates the metadata/protection envelope and most-used classifications for that batch. Each item has exactly one evidence file. A later sibling of a publication already processed in this run refreshes its envelope before provider work, because the earlier file may have changed their shared bibliography or classification. This is a read-only snapshot refresh, not full-catalog discovery.

Both tasks advance past local deferrals; extraction uses a composite queue cursor and evaluation an MD5 cursor. `--limit` counts publications for extraction and files for evaluation. Source/per-MIME/retry flags are rejected. Missing metadata, completed file decisions, pending reviews and unusable evidence stay outside evaluation discovery; returned unusable metadata is skipped and reported. `inventory_exhausted` describes exhaustion after the run cursor, not absence of deferred work. Owners: [navigation](navigation.md), [evaluation lookup](evaluation-navigation.md).

Extraction prefers selected then MD5-ordered complete unrestricted evidence and tries another file after preparation failure; evaluation processes each eligible file independently. Provider rejection ends only the current item. Privacy, incompleteness and filenames do not make a decision about other files; evaluation retains Tatar filtering and content/metadata applicability.

Read normalized relations, never write adapter views. Inclusion/evaluation provenance, privacy/accessibility/extraction/storage belong to files; bibliography and classification belong to publications. Publication inclusion is derived from included files. Recheck file/publication revisions, membership, eligibility, metadata and upstream snapshots before short mutations. Provider calls hold no PostgreSQL connection.

Honor field protections. Preserve IDs/reviewed resolution for unchanged contributions; removing/rewriting confirmed occurrences enters review. Generated names/contributions stay unconfirmed and source-script spellings remain AI input. Normalize languages, credit groups, accessibility, sufficient modes, reference URLs; preserve order, empty groups, absent/empty URLs, and non-ISBN identifiers.

Initial extraction fills absent metadata with validated output and records evidence-document method. Reassessment receives current metadata and returns an evidence-supported partial patch: omitted/null fields retain existing values, replacements require contradictory source evidence, and changed lists retain unaffected members. It uses the same evidence/page settings, validates merged metadata, and preserves inclusion, evaluation, classification and the original extraction method. Reassessment adds method evidence under `library.metadata_extract.reassessment`. It resets only the evidence file's earlier unprotected automatic inclusion/evaluation to pending, preserving shared classification and sibling decisions; protected conflicts become proposals. Evaluation atomically commits permitted patches/inclusion/method/taxonomy/evidence. Reuse taxonomy IDs; new paths are pending Gemini classifications. Validate the protected merged envelope. Pending task metadata proposals pause both tasks until reviewed.

## Persistence and protections

Both tasks retain the normalized envelope, contribution identities, classification path, and publication/document protections alongside each source snapshot. Python prepares and validates the expected protected result before opening a write transaction. Shared `app/catalog/metadata_save.py` submits one parameterized simple-query batch containing the repository-owned anonymous SQL block in `metadata_save.sql`; it installs no function and changes no schema. PostgreSQL's implicit transaction spans the complete batch, including the result SELECT, so no separate BEGIN or COMMIT request is needed. Pool connection establishment/liveness checks are outside that batch.

The batch acquires the existing document advisory lock, locks document/publication/location rows, and rechecks the complete selected snapshot, metadata presence for the operation, whole-publication admin protection, eligibility, and pending reviews. It bulk-writes permitted normalized relations while retaining unchanged contribution IDs/resolutions and non-ISBN identifiers, records proposals/evidence/method, and compares the stored normalized envelope and remaining source inputs against the validated plan before committing. Evaluation also acquires the taxonomy lock before document/row locks, reuses matching classification/node IDs or creates pending Gemini classifications, and stores file inclusion/evaluation provenance and publication classification atomically. Rejecting a file preserves shared classification. Decision proposals distinguish `document` changes (identified by evidence MD5) from `publication` changes. Protected decision changes become one proposal; accepted and retained classification paths participate in merged-envelope validation. Evaluation preserves the document's extraction method and revises it for permitted accessibility or inclusion/evaluation changes. Both Schema.org and decision evidence are retained. All checks, taxonomy work, metadata/decision writes and returned proposal IDs happen within that same request. Conflicts abort the batch. SQLite checkpoints clear only after acknowledged success. Unacknowledged commits are never automatically replayed: a later fresh discovery reconciles PostgreSQL truth.

## Retry state and output

SQLite owns attempts/deferrals/exclusions under `library.metadata_extract.catalog.v1` and `library.metadata_evaluate.catalog.v1`. Checkpoint identity includes publication ID, evidence hash, and prompt contract. Historical metadata-quality caches, MD5 checkpoints, and failure files are untouched and unused. Changed evidence/prompt/model pools reopen eligible work; resume untried models and clear checkpoints only after durable results/proposals commit.

Use [shared Gemini](../../../../docs/gemini-runtime.md). Content/schema failures consume model attempts; quota/service/storage/database/stop outcomes do not content-exclude. Exhausted items defer while others continue; global provider unavailability preserves untouched work. Authentication/configuration/unexpected implementation failures fail the run. Cancellation/finalization follow shared runtime rules.

Both tasks' `/settings` editors save candidate limits, a Gemini response deadline (1–900 seconds), and separate first/last visual page counts directly to private YAML; values survive restarts. Extraction uses `metadata.response_timeout_seconds`, `first_pages`, and `last_pages`. Evaluation has independent `metadata.evaluation_response_timeout_seconds`, `evaluation_first_pages`, and `evaluation_last_pages`; editing one task does not change the other. Either visual end can be zero, but both cannot be zero. Evaluation page counts apply to DjVu and PDF fallback evidence; usable extracted text retains its configured excerpt policy. The deadline starts after preparation, uploads, file activation, and provider admission/spacing, and covers generation and the full response stream. It excludes cleanup and catalog writes. A timed-out response cancels asynchronous transport, defers the current item operationally, and continues to another item without recording a content exclusion. Record effective settings in summaries and log response start/end elapsed time. Both tasks include page counts in the prompt contract version so earlier content attempts do not exclude changed evidence.

Run workspaces retain `items.json` and corruption-plan artifacts. Summaries link file/publication outcomes, source MD5s, review IDs, and per-model attempts/successes; common stdout/progress/artifact policy lives in root/runtime rules.

Extraction logs validated model-returned Schema.org as indented JSON, identified by publication ID, source MD5, and model, through shared redacted stdout logging before the guarded catalog save. Evaluation logs its validated, normalized response the same way, including applicability, reason, metadata patch, DDC, and category path. These logs describe model results; the subsequent item outcome reports whether the guarded save succeeded or requires review.

Request assembly and reassessment parsing live in `runtime/metadata/processing_request.py`; the runner owns provider execution, retries, and checkpoints. `app/catalog/schema_org.py` owns shared validation directly. Catalog discovery and saves share the nonmutating classification projection in `app/catalog/metadata_projection.py`. `app/catalog/metadata_records.py` distinguishes discovered evidence from prepared sources with required snapshots and checkpoint identities.

## Extraction evidence and validation

- Populate MD5-verified cache misses only from primary Backblaze; never mutate storage URLs/upload metadata ZIPs.
- Preserve extraction prompt, Schema.org contract, PDF edge slicing, and normalization. Sanitize database-owned `library_upstream_metadata` in text/visual requests.
- Absent title requires another bibliographic/content signal and valid `inLanguage`. Initial extraction never overwrites existing metadata; reassessment retains values absent from its evidence and never erases language with null.
- Strict JSON-LD validation precedes writes. Genre/audience/classification/role facets are English; descriptions follow `inLanguage`. Never truncate fractional page/age counts.
- Extraction and evaluation request publisher names without double quotation marks. Both response paths remove `" « » “ ” „ ‟ 「 」 『 』 ＂` throughout the name before validation, collapse whitespace, and trim; empty results are omitted. Existing unknown-value handling is retained. Apostrophes and square brackets remain. The shared publisher-name normalizer owns this repair; other names and prose retain their punctuation.
- Tatar language tags (`tt` or `tat`) require an explicit script subtag; reject unspecified-script tags rather than guessing Cyrillic. Apply this to every language in multilingual metadata and to source-work references. Other languages may retain valid language-only tags.
- Reject generic `tt-Latn` / `tat-Latn` in responses; request the source-evidenced Zamanalif or Yanalif tag. Do not infer the orthography during normalization. Remove the generic tag from private YAML evaluation languages. Resetting metadata and file evaluation does not require deleting preview requests, preview pages, or their stored images; those remain keyed to the source MD5.
- Publication dates follow the [catalog year-only contract](../../../../docs/database-reference.md#primary-tables-and-fields). Extraction and evaluation request `datePublished` as `YYYY`; postprocessing reduces year-month/full dates (including slash-separated forms) to the year before response validation. Model years retain the 1500–2100 range; uncertain, malformed, or unsupported values are omitted rather than inferred. Evaluation accepts integral numeric years but never searches free text for a year. Response schemas and merged-envelope validation require four ASCII digits.
- Reject mixed scripts only at two-to-one competing dominance; treat `Ьь` as Yanalif and preserve `tt-Latn-x-zaman`.
- Zamanalif uses the private-use tag `tt-Latn-x-zaman`; normalize both former spellings to it before validating extraction responses, including multilingual values and source-work references. Stored envelopes require the canonical spelling. Private YAML `sup_langs.tt.codes` must use that same tag for exact-match evaluation discovery.
- Deterministic PDF open/page-tree/page-read failure may create guarded `corrupted` plans; active cleanup excludes sources. Password protection/service/storage failures defer operationally; Maintenance executes cleanup.
- PDF/DjVu visual extraction uses configured first/last counts, unique overlapping selections, and source order. Either end can be zero, but both cannot be zero. DjVu is visual-only: verified sources rendered to PDF, reduced size below Gemini limits. Ignore extracted DjVu content; missing tools/timeouts are operational failures.

## Evaluation evidence and validation

- Preserve valid positive/negative decisions. Select pending file inclusion or included files without publication classification. An excluded file may retain the classification shared with included siblings; this is not an inconsistent decision. Missing metadata awaits extraction; existing unusable metadata defers evaluation as `unusable_metadata` and requires explicit correction.
- Use database upstream evidence, never remote fetching/Yandex source fallback.
- Require explicit boolean/reason; applicable responses also require normalized DDC/English category path. Validate the merged envelope, not just patches.
- DjVu uses evaluation's configured first/last rendered pages; PDF uses those counts when text is unavailable. Overlap appears once in source order. Unpreparable evidence defers.
- Report file/skipped/terminal/deferred counts and per-model attempts/successes; log publication ID, source MD5, resolved model before requests.

## Admin validation

`CatalogRepository.validate_publication_metadata(publication_id, revision=..., actor=...)` is the backend-only admin command; trusted callers supply the admin identity. It locks and checks the publication revision, rejects merged publications and pending/deferred metadata proposals, validates all document projections, and atomically records validation evidence and sets the queue position to `-1`. There is no unlock command or admin UI. Existing property protections remain independent; migration does not infer admin validation from them.

Whole-publication protection excludes extraction/reassessment and is rechecked at save time. An in-flight response with an older revision cannot overwrite a newly validated publication. Evaluation ignores bibliographic patches and retains classification for validated publications while still processing pending file inclusion. Included protected files without classification do not re-enter evaluation solely for classification. Existing personality normalization creates identity hypotheses without resolving contributions or rewriting publication metadata; it must retain that boundary. General automated metadata replacement also rejects admin-validated publications.

Revision `20261106_0069` adds one queue column and its sequence, initializes absent metadata to `0` and existing metadata to `1`, and preserves property protections. Apply through normal interactive migration bootstrap; scheduled task preflights require this revision and never migrate. No historical review-count backfill is needed. The migration accepts compatible manually completed steps, updates only remaining metadata-present rows at `0`, and never resets existing positive positions or admin protection. The [database tools contract](../../../../docs/operations.md#database-tools) owns recovery and manual-step guidance.
