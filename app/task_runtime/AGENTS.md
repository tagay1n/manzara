# Task runtime guidance

These rules apply to `app/task_runtime/`. Shared contracts also cover `app/tasks.py` and `app/run_artifact_channel.py`.

- Batch runs default to writing `~/.manzara/logs/task-runs/<task_id>/run-<run-id>.log`, or the equivalent configured artifacts-root path. The Backblaze workflow selects `run_batch(log_to_file=False)` for stdout-only logs without a log path. This file is the authoritative verbose batch log. New interactive runs use terminal scrollback only, without optional file capture; preserve existing log files and history.
- `RunLogSink` owns callable logging with level, flush/close lifecycle, and an optional file path. Preserve flow-facing `RunContext.log`, `LOG_SINK` routing, and shared redaction. File sinks retain timestamp, level, run/task/panel/source context, and message; terminal sinks use compact formatting with visible severity. Omit absent log paths from summaries.
- Do not persist stdout/stderr or `task.log` events in either database. Retained file readers serve bounded pages using run-local cursors.
- Coalesce progress snapshots on the local `runs` row. Do not duplicate snapshots as `task.progress` events.
- Log start, per-item, decision, failure, and final-summary boundaries. Include stable identifiers for successful mutations.
- Never derive structured artifacts by parsing logs. Persist compact `task.artifact` events in local SQLite and save large details in run artifacts. Artifact writers create their own parent directories independently of log sinks. HTTP/SSE transport is retired.
- CLI tasks run in background threads with explicit run contexts and cooperative cancellation. Share one bounded PostgreSQL engine; never mutate per-task process environment or redirect global stdout. Propagate the run log context into worker threads.
- Noninteractive batches use the same `TaskRunner` and persisted task/artifact contracts. `batch.py` owns local session locking, recovery, sequential stages, signals, and cooperative time budgets; command boundaries supply flow descriptors and read-only preflight checks. Inspect terminal state only after worker finalization completes, and return nonzero for incomplete or failed runs.
- Batch logging sends each redacted structured line directly to stdout and, when enabled, its log file, flushing each immediately. Stdout-only workflow logging retains structured artifact events and result files independently of logs. Periodic batch status snapshots are console-only. Interactive logging uses a bounded thread-safe queue with backpressure and one terminal consumer; redact before enqueueing, preserve message order, and drain before reporting completion or exiting. Renderer frames and transcript messages share a nonblocking terminal writer; keep raw input attached and coalesce redraws during backpressure. Output failure unblocks producers, requests safe stop, and returns CLI exit code 1. Keep the consumer alive during cooperative shutdown; do not join a worker on the UI loop. Force exit restores input mode and exits without waiting for renderer flushes or buffered-stream locks. Console output does not create database log events or structured artifacts.
- Interactive composition sets `max_active_runs=1`; enforce it under the start lock through thread finalization. The CLI also owns its foreground slot from the initial request through output drain. Task/history selection must not replace foreground identity. Local finalization flags and UI pending actions are presentation inputs, never new persisted workflow states.
- Task descriptors own grouping, worker defaults, worker limits, complete-inventory requirements, and Python handlers. Reject candidate limits for complete-inventory tasks before creating a run. Do not persist task/panel definitions, icons, shell commands, or one-shot worker overrides. The retained `panel_id` run/event/log field identifies a task group; it has no dashboard definition or rendering owner.
- CLI startup initializes only SQLite and checks the catalog read-only. PostgreSQL migrations remain a separate operation. Hold the local session lock before recovery. Schema version 7 recreates older local runtime databases under the owner-approved fresh-state policy documented in `docs/operations.md`; subsequent startups retain run history and retry state.
- Preserve graceful stop boundaries, restartable checkpoints, redaction, and actionable error context in run state, logs, and events.
- Use `after_log_id` for follow and `before_log_id` for backfill. Keep reads bounded.
